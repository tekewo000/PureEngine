# C#・Vulkan 2D描画の実装計画

作成日：2026-09-22

**状態：計画作成済み。Vulkan描画・Scene Viewへの埋め込み・単体実行は未実装、実機検証も未実施。**

この文書は作業順と各段階の完了条件を管理する。描画の設計方針と適用範囲の正本は [EngineArchitecture.md](EngineArchitecture.md#ui描画プレビュー設計方針実装は未着手)、全体の進捗・検証証跡は [ImplementationPlan.md](ImplementationPlan.md) とする。以下のクラス名・プロジェクト名は実装案であり、既存APIではない。

## 1. 到達目標

UnityのCanvas・RectTransformに近い感覚で、Scene Viewに画像・文字・ボタンを配置し、Inspectorで編集してシーンへ保存する。Play時は編集データと分離した実行用シーンを同じ描画処理で表示し、ボタン操作から普通のC#ゲームコードを実行する。単体実行でも同じ描画・UI・Runtimeを利用する。

最小の完成例は「カード画像、日本語の得点表示、得点を増やすボタン」。配置・保存・再Open、Play／Stop／再Play、Editorなしの起動までを一続きで確認する。

Scene Viewへの表示を本実装の前提条件とし、別ウィンドウに絵が出ただけでは描画方式の検証完了にしない。

## 2. 前提と未決定事項

| 項目 | 計画上の扱い |
| --- | --- |
| 描画本体 | リポジトリ固定の.NET SDK 11 RC1／net11.0／C#15で実装する |
| 描画API | Vulkanを採用する方針。Core／Runtimeには依存を追加しない |
| Editor | 既存のAvalonia 12.1.2を出発点とする。ゲーム内UIをAvaloniaのButton等へ変換する方式は採用しない |
| 最初の対象 | Windows x64を検証対象とする案。他OSの対応保証は今回の完了条件に含めない |
| C#バインディング | Silk.NET.Vulkanを第一候補としてV0で選定する。バージョン・必要拡張・保守状況を確認して固定する |
| シェーダー | HLSL→SPIR-Vのビルド時コンパイルを第一候補とする。言語とコンパイラはV0で確定する |
| GPU／Vulkan要件 | Vulkanの最低バージョン、必要な外部メモリ・同期機能、対応GPUをV1の実測後に記載する |
| 画像・文字 | 画像デコード、フォントの字形生成・シェーピングは既存ライブラリを候補比較する。日本語を初期の検証対象にする |
| 素材・レイアウト形式 | V3で保存形式とAPIを具体化し、設計書へ反映してから実装する |

「C#15で実装」は自作するCPU側の描画コードを指す。Vulkanローダー・GPUドライバー・採用ライブラリのネイティブ依存は残る。通常のC#15をそのままGPUで動かすものではなく、C#からSPIR-Vを生成する独自コンパイラは今回作らない。自作のC++層は設けない。

ゲーム用csprojは `LangVersion=15.0`、Editor内コンパイラはRoslyn 5.xのPreview設定（C#15相当）であり、エンジン本体のC#15と揃っている。今回の描画ライブラリをC#15で書くことの前提にしてよい。

## 3. 責務と既存機能の接続先

| 場所 | 役割・変更範囲 |
| --- | --- |
| PureEngine.Core | 保存可能なUI・画像のデータ、ID参照、親子関係、画面に依存しない配置計算・入力規則。GPUハンドルやAvalonia型を公開しない |
| PureEngine.Runtime | 既存のGameSession／PlaySessionとライフサイクルを再利用する。描画のためにStart／Update／Destroyを別実装しない |
| PureEngine.Rendering（新規案） | Vulkanの初期化・描画・画像と文字のGPU資源・寿命管理。Editorに依存しない |
| PureEngine.Editor | 既存のSceneViewport／GameViewportへ表示を接続。Scene Viewの編集入力・選択枠・Inspector連動、GPU画像のAvaloniaへの受け渡しを担当する |
| PureEngine.Player（新規案） | 単体実行の起動・ウィンドウ・入力・終了。RenderingとRuntimeを使い、Editorへの参照を持たない |

EditorとPlayerが共有するのは描画コード・ゲームデータ・入力規則であり、プロセスをまたいだGPU資源共有ではない。Scene ViewとGameの描画先・入力状態・参照するシーンは分ける。デバイスや不変素材の共有は、所有者と解放条件を明確にした範囲だけで行う。

既存の接続先は次を優先する。

- `MainWindow.axaml` の `SceneViewport`／`GameViewport`：現在は空の表示領域。
- `EditSceneStore`、`MainWindow.Persistence`、`SceneSerializer`：編集・未保存・保存・シーン差し替え。
- `MainWindow.Play`、`PlaySession`：Playの準備・更新・自動停止・手動停止・終了処理。
- `UserCodeReloadCoordinator`、`ProjectComponents`：再コンパイル時のScene移行・型登録・古いコードの解放。
- `UserCodeCompiler`、`ProjectCodeWorkspace`：ゲーム向けAPIを別アセンブリに置く場合のコンパイル参照・生成csprojへの反映。
- `Log.Engine`／Console：描画初期化・実行失敗の報告。

単一のVulkan実装から始める。将来のDirectX／OpenGL用の汎用バックエンド体系やRender Graphは先に作らない。親子・保存・シーン移行は既存の仕組みを拡張し、描画側に第二の保存シーンを作らない。

## 4. 実装順と完了条件

順序は **V0 → V1 → V2 → V3 → V4 → V5 → V6**。各段階を検証してから次へ進み、特にV1が不成立ならUI機能の本実装へ進まない。

### V0：依存関係と描画先の設計を確定する

- [ ] 実機のOS・GPU・ドライバー・Vulkan機能、既存Avaloniaの描画バックエンドを記録する。
- [ ] C#バインディング、シェーダーコンパイラ、単体ウィンドウの生成方法を選び、ライセンス・配布物・固定バージョンを記録する。
- [ ] 既存Avalonia版で利用できるGPU interop APIを実際のパッケージ／公式サンプルで確認する。最新Web資料のコードをそのまま使えるとは仮定しない。
- [ ] Vulkan画像の共有形式、アダプターの一致条件、外部ハンドル、画像レイアウトとキュー所有権、待機／通知の同期方式、資源の所有者を決める。
- [ ] 日本語フォントの取得・ライセンス、字形生成・シェーピング・改行の候補を小さな文字列で評価する。文字入力とIMEは表示処理から分ける。
- [ ] 採用する言語・ライブラリ・表示経路を設計書へ反映する。

完了条件：C#15の小さな試作がビルドでき、単体表示とEditorへの受け渡しをどう検証するか説明できる。Vulkan非対応時は描画だけを利用不可にし、理由を示して既存編集機能を維持する方針を定める。

### V1：Scene Viewへの埋め込みを実機で成立させる

- [ ] 共有する最小の描画処理で、色付き図形とテスト画像をGPU上の画像へ描く。
- [ ] AvaloniaのGPU interopでその画像を `SceneViewport` 内へ表示する。別ウィンドウへの表示だけでは代替しない。
- [ ] 試作用の単体ウィンドウでも同じ描画内容を表示する。ウィンドウ表示用の処理と、図形を描く処理を切り分ける。
- [ ] ペインの連続リサイズ、サイズ0、最小化／復元、Scene View／Gameのタブ切替、表示領域の取り外し／再作成を確認する。
- [ ] DPI倍率・表示領域のピクセル寸法・ポインター座標の変換を確認する。
- [ ] Avaloniaの上に選択枠を重ねられること、入力が隣のInspectorを妨げないことを確認する。
- [ ] Validation Layersで寿命・同期・画像レイアウトの誤りを確認し、実装由来のエラーを解消する。

完了条件：既存Editor内で表示が成立し、上記操作後も破損・クラッシュ・デッドロックなく描画を再開できる。GPU／ドライバー、API・拡張、再現手順、画面の証跡を残す。

通常経路で毎フレームGPU画像をCPUへ読み戻す方式は完了扱いにしない。GPU共有が成立しない場合は、原因と代替経路の制約を記録し、表示方式を見直してから続行する。別GPUや別OSでも動くという保証にはしない。

### V2：最小の2D描画とGPU資源管理

- [ ] 色付き矩形・画像・文字を、位置・回転・拡縮・色・透明度・描画順・矩形クリップ付きで描く。
- [ ] 透明物の順番を保持してまとめて描画する。テクスチャ単位の並べ替えで見た目を壊さない。
- [ ] 色空間、アルファの扱い、座標の原点・軸方向、画素と論理座標の関係を決め、EditorとPlayerで共有する。
- [ ] 日本語・英数字・句読点・改行を表示し、欠落文字の代替表示、フォントサイズ・行間・幅指定の折り返しを扱う。
- [ ] 文字のGPUアトラスを必要に応じて更新し、キャッシュの所有者・容量制限・破棄条件を定める。
- [ ] GPUが利用中の画像・バッファを先に解放しない。初期化途中の失敗、再作成失敗、終了時にも生成済み資源を解放する。
- [ ] デバイスロスト・共有非対応・描画失敗では無限再試行せず、描画を停止して原因を報告する。自動的なデバイス再構築は初期範囲に含めない。

完了条件：画像と日本語を含む固定サンプルを、Editorと単体ウィンドウで同じ配置・色・クリップで表示できる。資源の作成・再作成・解放を繰り返して継続的な資源増加がないことを確認する。フォントと画像はライセンスを確認した同じ素材を配布する。

### V3：親子・素材参照・UIデータを保存できるようにする

- [ ] Parent、兄弟順、循環の拒否、親削除と付け替え時の子の扱いを設計し、Sceneの操作・実行時予約・YAML・Cloneへ一貫して反映する。
- [ ] オブジェクト・画像・フォントをIDで参照する最小の仕組みを作る。Project内の素材位置への対応、改名・移動、欠落時の表示、Project外参照の拒否を扱う。
- [ ] Canvas相当の画面設定と、RectTransform相当のAnchor・Pivot・位置・サイズ・回転・拡縮を定義する。既存TransformとUI矩形の役割を区別する。
- [ ] 基準解像度と画面サイズ変更時のルール、親のクリップ・子の配置・非表示・描画順を確定する。初期対応は画面上の2D UIとし、World Space Canvasは含めない。
- [ ] Image・Text・Button相当を普通のC#コンポーネントとして扱う。描画・操作と保存する設定を分け、GPUハンドル・イベント購読・一時状態を保存しない。
- [ ] ボタンからゲームコードへの接続方法と対象の参照方法を決める。文字列のメソッド名だけで曖昧に呼び出す接続は避ける。
- [ ] Inspector対応型の追加が必要なら保存・Clone・コード再読み込みも一緒に対応する。描画型だけの特別な保存経路を増やさない。
- [ ] Parent等がない既存シーンの読み込みと保存互換、必要なversion変更を確認する。

完了条件：GPUを使わないチェックで、親子の座標変換・Anchor／Pivot・ID参照・保存往復・Clone分離・不正データ拒否を確認できる。親を動かすと子も動き、保存と再Openで再現する。

### V4：Scene Viewで配置・編集する

- [ ] 編集用Sceneのデータを描画へ渡し、Inspectorの変更とSceneの差し替えを反映する。Start／Updateは呼ばない。
- [ ] Scene Viewのパン・ズーム、選択、移動・サイズ変更・回転のハンドルを実装する。視点変更は制作データを変えない。
- [ ] UI作成操作、Stuffsの親子ツリー、InspectorとScene Viewの選択をつなぐ。
- [ ] ポインターを表示領域からシーン座標へ変換し、回転・拡縮・クリップと重なり順を考慮して選択する。
- [ ] 編集ドラッグはクリックで開始、確定時に未保存化、Escで元の値へ戻す。フォーカス喪失時の中断も扱う。
- [ ] C#再読み込みで採用された新Sceneに表示を切り替え、失敗時は旧状態を保持する。描画キャッシュに古いユーザー型・インスタンスを残さない。

完了条件：画像と文字をScene Viewで配置し、Inspectorで調整して保存・再Openできる。選択と入力がEditorの別ペインに漏れず、ゲームのボタン処理は編集中に動かない。

### V5：Game表示・入力・Play／Stopを接続する

- [ ] 既存 `PlaySession` が保持する実行用SceneをGameに表示する。Scene Viewは編集用Sceneを表示し、Play中の編集禁止を維持する。
- [ ] 初期段階では既存の更新経路を再利用し、描画コールバックでゲームのUpdateを追加実行しない。非表示タブの描画停止とゲームの進行を区別する。
- [ ] 入力をゲーム更新の境界で処理し、表示へ反映する順序を定める。GPU／合成側には確定済み描画データだけを渡し、可変Sceneを並行して列挙しない。
- [ ] ボタンの通常・ホバー・押下・無効状態、ポインターキャプチャ、フォーカス喪失、Tab移動とキーボード操作を扱う。
- [ ] クリック処理中のオブジェクト削除・停止と例外を既存の終了規則につなぎ、Consoleへ報告する。
- [ ] Stop・自動停止・開始失敗・Project終了の全経路で、入力／描画要求を止め、既存のDestroy→Component Dispose→サービス解放順を守る。GPU側の参照完了後に対応する資源を解放する。
- [ ] 再Playは新しい実行用Scene・入力状態から開始し、前回の購読や押下状態を引き継がない。

完了条件：ボタンで得点が増え、Stopで編集値は変わらず、再Playで初期値に戻る。エラー停止を含めて20回のPlay／Stop後も重複クリック・資源の継続増加・同期エラーがない。

### V6：同じプロジェクトを単体実行する

- [ ] 保存された起動シーン、型ID登録、ゲームアセンブリ、サービス登録、素材、シェーダー、フォントを実行用の出力へまとめる。
- [ ] 必要なProject読込・型解決・ビルド処理は既存Editorから最小限共通化する。PlayerがEditorを参照する構成や、別仕様のコンパイラ・Serializerを作らない。
- [ ] Playerで同じ入力規則・PlaySession・Renderingを起動し、ウィンドウ終了時に確実に停止・解放する。
- [ ] SDKやVulkan SDKの開発ツールがなくても動く配布構成を選び、.NETの同梱方式、必要なGPUドライバー、ネイティブ依存、ライセンスを明記する。
- [ ] Project移動後も素材とコードを解決できること、不足素材・未対応GPU・起動失敗時に原因を表示できることを確認する。

完了条件：Editorを終了した状態で、出力先から最小完成例を起動・操作・終了できる。Gameビューと同じ論理画面サイズで配置・描画順・操作結果が一致し、EditorのDLLを要求しない。

## 5. 検証と記録

### 自動検証

- 各C#変更後に、既存の `./tools/code-quality.ps1 -Check` を実行する。namespaceと診断規約は [AGENTS.md](../AGENTS.md) に従う。
- GPU不要の配置計算、参照・保存互換、描画命令の順序、入力・Play分離は既存Checksへ必要なチェックを追加する。
- GPU検証は明示的に実行する経路を設ける。GPUのない通常CIで未実行になった項目をPASSと記録しない。Core／Editor Headlessの成功をVulkan表示の証拠にしない。
- シェーダーは固定したツールでビルドし、コンパイル失敗・不足成果物を検出する。通常配布時に実行時シェーダーコンパイルを要求しない。

### 実機検証

- V1の表示・リサイズ・DPI・タブ切替と、V5の入力・停止・再開を実際の画面で確認する。
- まず手元のGPUで検証し、別ベンダーのGPUは機材が用意できた時点で追加する。対応範囲は試した構成だけ記録する。
- 検証用の負荷目安は1280×720、半透明画像100枚、日本語テキスト20要素とする。件数・フォント・DPI・GPU・ドライバーを記録し、CPU更新／描画準備、GPU時間、割り当て量、GPU資源量を測る。
- 60fps相当の16.7msを初期の評価目安にするが、測定前に性能保証とはしない。文字追加やリサイズ直後と、定常状態を分けて記録する。

### 証跡の置き場所

`ImplementationPlan.md` に段階ごとの実装コミット、チェック結果、実機環境、操作手順、画面証跡、残る制限を記載する。実装済み・ローカル自動チェック済み・CI確認済み・GPU実画面確認済みを分ける。

操作が利用可能になった段階でREADMEに起動・配置・素材取込・ビルド手順を追加する。現時点で存在しないコマンドを利用手順として掲載しない。

## 6. 今回含めないもの

- 3D、照明・影、物理、骨格アニメーション、World Space Canvas。
- 複数の描画バックエンド、Render Graph、独自シェーダー言語、シェーダーのC#15完全対応。
- 汎用Prefabシステム、フル機能の自動レイアウト、汎用Undo／Redo、UIアニメーション編集ツール。
- 入力欄・日本語IME・リッチテキスト。文字の表示・ボタンのキーボード操作は今回に含める。
- 通信、Steam、複数プレイヤー起動、他OS対応、配布ストア向けパッケージ。

上記を後から足せることだけを理由に、先行して抽象化や設定を増やさない。必要になった機能ごとに設計と検証範囲を追加する。
